# Walkthrough: `factor(15)` to a Verified Quantum Circuit

This walkthrough takes `factor(15)` through QCLP_G end to end. It
generates a `.clp` file, inspects it, runs a Grover search on the fast
simulator, exports it to OpenQASM 3.0, and runs the circuit on the
gate-level statevector simulator. No step solves the problem
classically first: the searches do not know how many solutions there
are. Every block of output was captured from the current code
(SWI-Prolog 9.0.4, 1 Oct 2026). Every command is described in full in
`User_Guide.md`.

---

## 0. Two separate pieces

- **The application** (`qclp_gates/`, loaded by `[load]`) only ever
  reads `.clp` files. It knows nothing about `factor(N)` or any other
  named problem.
- **`examples/generators.pl`** is a separate tool that writes `.clp`
  files for a few parametric families.

So "running `factor(15)`" is two steps: generate the file, then run it.

---

## 1. Generate the `.clp` file

```prolog
?- ['examples/generators'].
?- gen_clp(factor(15), 'examples/factor15.clp').
```
```
[gen] .clp written: examples/factor15.clp  (3 goal(s))
```

The file:

```prolog
%% Generated by examples/generators.pl: gen_clp(factor(15)).

problem_spec([
    fd_domain(p,2,14),
    fd_domain(q,2,14),
    fd_product_eq(p,q,15)
]).
```

`p` and `q` range over 2..N−1; 1 and N are left out as trivial factors.
The one constraint is p × q = 15. (`examples/factor15.clp` ships
already generated.)

---

## 2. Inspect it

Load the application (in the same session, or a new one started in the
`QCLP_G` directory):

```prolog
?- [load].
?- info('examples/factor15.clp').
```
```
=======================================================
  QCLP_G -- Constraint Summary
=======================================================

  Domains:
    p  in  2..14  (13 values, 4 qubits)
    q  in  2..14  (13 values, 4 qubits)

  Constraints:
    p * q  #=   15

  Qubit budget:
    p: 4 qubits to hold values up to 14 (domain 2..14)
    q: 4 qubits to hold values up to 14 (domain 2..14)
  Registers share the widest width: 2 x 4 qubits
  Total domain qubits: 8
  + 1 oracle flag qubit
  = 9 qubits minimum
=======================================================


=======================================================
  QCLP_G -- Grover Circuit Statistics
=======================================================
  Variables:          2  (2 searched, 0 fixed)
  Constraints:        1
  Search space N:     169
  Circuit registers:  2 x 4 qubits = 256 register states
  Default iterations: 12  (optimal if exactly 1 state is marked)
  Domain qubits:      8
  Total qubits:       9 (+ ancilla)
  (The number of solutions is not computed: it is unknown, as on
   real hardware. run/1,2 search with unknown M.)
=======================================================
```

13 values up to 14 need 4 qubits per register. The problem has
13 × 13 = 169 declared assignments, but the registers hold
16 × 16 = 256 combinations, and the oracle rejects the 87 outside
2..14 with range checks on the register bits. Both simulators search
the 256 register states. The default
iteration count for an exported circuit, 12, is the best for one
marked state among 256: without solving the problem there is no better
guess (`User_Guide.md` §7).

## 3. Search on the fast simulator

```prolog
?- run('examples/factor15.clp', [seed(1), top(4)]).
```
```
[rp] examples/factor15.clp
[grover] circuit oracle (pcode): 2 registers x 4 qubits = 256 register states
[grover] exponential search (unknown M), budget 144 oracle calls
[grover]   round 1: K=0, measured |198> [p=6,q=12]: checked, not a solution
[grover]   round 2: K=0, measured |151> [p=7,q=9]: checked, not a solution
[grover]   round 3: K=1, measured |127> [p=15,q=7]: checked, not a solution
[grover]   round 4: K=1, measured |40> [p=8,q=2]: checked, not a solution
[grover]   round 5: K=0, measured |15> [p=15,q=0]: checked, not a solution
[grover]   round 6: K=1, measured |73> [p=9,q=4]: checked, not a solution
[grover]   round 7: K=0, measured |9> [p=9,q=0]: checked, not a solution
[grover]   round 8: K=3, measured |53> [p=5,q=3]: checked, a solution
[grover] found [p=5,q=3] after 6 oracle calls

Final state after K=3 (simulator view, not measurable on hardware):
Top 4 of 256 register states by probability:
  |53>     16.8577%  [p=5,q=3]  ** solution **
  |83>     16.8577%  [p=3,q=5]  ** solution **
  |0>       0.2610%  [p=0,q=0]
  |1>       0.2610%  [p=1,q=0]
```

Each round runs K Grover iterations, K drawn at random from a range
that grows by 6/5 per failed round, then measures one state and checks
it. The eighth round found 5 × 3. The search would have stopped and
reported "probably none" after 144 oracle calls (9·√256).

The fast simulator does not simulate gates. Its oracle is the
circuit's oracle microcode, which `show/1` prints:

```
-- Oracle Microcode (circuit) --
  next(fd_anc1, p*q)
  flag_test(fd_anc1, eq_const(15))
  flag_test(p, in_range(2,14))
  flag_test(q, in_range(2,14))
```

That is: put p × q into an 8-qubit register, test it for 15, and test
that p and q lie in 2..14. A state is marked only if every test passes.

It evaluates these steps for each of the circuit's 256 register states,
in the circuit's register widths, so it marks exactly the states the
circuit's oracle marks. Measured states such as p = 15, q = 0 come from
those register states: the registers can hold them, and the range
checks stop the oracle marking them. The state indices are the
circuit's: |53⟩ = `0011 0101` is q = 3, p = 5.

## 4. Export the Grover circuit

```prolog
?- export('examples/factor15.clp').
```
```
Written: qasm/factor15.qasm  (search space 169, 256 register states, 12 Grover iterations)
```

The file is 326 lines long. It starts with the header and a gate
definition for the 4-bit multiplier. The product register `c` is 8
wires wide (`v_c0`..`v_c7`), because a 4-bit × 4-bit product needs 8
bits:

```qasm
OPENQASM 3.0;
include "stdgates.inc";
// Generated by QCLP_G -- structured Grover circuit

// Search space: 169 states
// Register states: 256 (2 search registers x 4 qubits)
// Grover iterations: 12
// Iterations: optimum for one marked state (number of solutions unknown)
// Example: examples/factor15.clp

// -- Gate definitions ----------------------------

gate mul_4bit v_a0, v_a1, v_a2, v_a3, v_b0, v_b1, v_b2, v_b3, v_c0, v_c1, v_c2, v_c3, v_c4, v_c5, v_c6, v_c7, v_mul_t0, v_mul_t1, v_mul_t2, v_mul_t3, v_mul_t4, v_mul_g0 {
    // mul c = a * b (4-bit, Cuccaro shift-and-add)
    ccx v_b0, v_a0, v_mul_t0;
    ...
```

Inside the oracle, the multiplier is called and then inverted
(compute, test, uncompute), so every ancilla returns to |0⟩. Its
product goes into the shared ancilla pool `anc_pool0`:

```qasm
    mul_4bit v_p0, v_p1, v_p2, v_p3, v_q0, v_q1, v_q2, v_q3, v_anc_pool00, ..., v_mul_g0;
    ...
    inv @ mul_4bit v_p0, v_p1, v_p2, v_p3, v_q0, v_q1, v_q2, v_q3, v_anc_pool00, ..., v_mul_g0;
```

After the gate definitions come Hadamards over `p` and `q` (uniform
superposition), then 12 rounds of oracle + diffuser, then measurement.
`export('examples/factor15.clp', Out, [iterations(K)])` writes a
circuit with another K.

## 5. Run the circuit on the gate-level simulator

### 5a. The exported circuit, as written

```prolog
?- run_qasm('qasm/factor15.qasm', [shots(100), top(5)]).
```

This takes about eight minutes:

```
[decode] circuit: qasm/factor15.qasm
[decode] problem: examples/factor15.clp
[sv] registers: [reg(v_p,0,4),reg(v_q,4,4),reg(v_anc_pool0,8,8),reg(v_oracle_flag,16,1), ...]  total qubits: 39
[sv] 39 qubits, 9152 gates
[decode] variables: p = qubits 0..3  q = qubits 4..7

Shot results (100 samples, 36 distinct assignments, top 5; each checked):
    35/100 (35.0%)  [p=5,q=3]  ** solution **
    30/100 (30.0%)  [p=3,q=5]  ** solution **
     2/100 (2.0%)  [p=11,q=10]
     1/100 (1.0%)  [p=0,q=0]
     1/100 (1.0%)  [p=0,q=1]
  ancillas: clean in every shot (uncompute OK)
```

The fast simulator predicts this in under a second:

```prolog
?- run('examples/factor15.clp', [iterations(12), analysis(true)]).
```
```
...
  |53>     32.0816%  [p=5,q=3]  ** solution **
  |83>     32.0816%  [p=3,q=5]  ** solution **
...
[analysis] every state checked classically -- diagnostics, not part of the search
  solutions in declared domain       64.16%   (2 states)
  wraparound solutions                0.28%   (2 states)
  non-solutions                      35.55%
```

What it tells you:

* **The circuit works.** 65 of 100 shots are factorisations, as the
  fast simulator predicts (64.16%). Every shot is checked against the
  constraint, and every ancilla is back at its starting value in every
  shot.
* **K = 12 was a guess.** It is the best K for one marked state; there
  are two, so 12 overshoots. Theory gives sin²(25θ) = 64% with
  θ = arcsin(√(2/256)). Knowing that K = 8 is best (99.6%) would require
  knowing that there are two solutions, i.e. solving the problem first.
  On hardware you would just run it again: one success is enough, and a
  shot is checked by one multiplication. The fast simulator shows
  quickly what any K gives (`iterations(K)`).
* **No wraparound.** The registers can also hold 1 × 15 and 15 × 1,
  outside 2..14. The range checks stop the oracle marking them: their
  0.14% each is the same as any non-solution's. Before 1 Oct 2026 there
  were no range checks, and those two took 45% of the probability.
* **What it costs.** 39 qubits and 9,152 gates (762 per iteration).

### 5b. Search with an unknown number of solutions

Rather than guess one K, run the exponential search on the circuit:

```prolog
?- run('examples/factor15.clp', [backend(exact), seed(5)]).
```
```
[exact] examples/factor15.clp: 39 qubits, 762 gates per Grover iteration, 256 register states
[decode] variables: p = qubits 0..3  q = qubits 4..7
[exact] exponential search (unknown M), budget 144 oracle calls
[exact]   round 1: K=0, measured [p=11,q=8]: checked, not a solution
[exact]   round 2: K=1, measured [p=3,q=10]: checked, not a solution
...
[exact]   round 15: K=8, measured [p=5,q=3]: checked, a solution
[exact] found [p=5,q=3] after 30 oracle calls (last round K=8)
```

Each round applies the real oracle and diffuser gates K times, measures
once and checks the shot. This took about five minutes.

### Reading the raw simulator output by hand

`qsim_run/2` and `qasm3_expand_and_run/2` print undecoded states:

```
  |00000000000000000000000000000083>  25/100 (25.0%)
```

That number is the index of the whole 39-qubit state. The
`[sv] registers:` line says `p` is qubits 0–3 and `q` is qubits 4–7, so
take the low 8 bits and split them (qubit 0 is the lowest bit):

| State | Binary (q · p) | p | q | p × q |
|---|---|---|---|---|
| 83  | `0101 0011` | 3  | 5  | 15 |
| 53  | `0011 0101` | 5  | 3  | 15 |

All the higher bits are 0, so the ancillas are clean. `decode/1` does
this for pasted lines (after `export`, it knows the circuit):

```prolog
?- decode('  |00000000000000000000000000000083>  25/100 (25.0%)').
```
```
[decode] layout from qasm/factor15.qasm (examples/factor15.clp)
  |83>  [p=3,q=5]  ** solution **  (ancillas clean)   25/100 (25.0%)
```

`run_qasm/2` runs the circuit and decodes every shot itself.

## 6. Recap: the pipeline in six lines

```prolog
?- ['examples/generators'].
?- gen_clp(factor(15), 'examples/factor15.clp').
?- [load].
?- info('examples/factor15.clp').
?- export('examples/factor15.clp').
?- run_qasm('qasm/factor15.qasm', [shots(100)]).
```

Generator → `.clp` → qubit inspection → QASM export → gate-level
simulation. Add `run('examples/factor15.clp')` for the fast simulator,
and `[backend(exact)]` for the search on the circuit. `solve/1` is a
classical cross-check, not a step of the pipeline.
